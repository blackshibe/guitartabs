# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — Vite dev server (typically port 5173)
- `npm run build` — `tsc -b` type-check then Vite build; run this to verify changes
- `npm run lint` — oxlint

`npm test` — vitest; unit tests live in `src/lib/__tests__/` (reducer/history, clipboard, songOps, progression, cell values, tunings, instruments, exportText, youtube, LZW, storage migrations). Pure-logic only — no component/DOM tests. A first-run `WelcomeDialog` (intro + controls, `tab-editor:welcomed` localStorage flag) shows once; its shortcut list is shared with `ShortcutHelp` via `lib/shortcuts.ts`.

## Architecture

Single-page guitar tab editor: React 19 + TypeScript, Vite, Tailwind CSS v4 (via `@tailwindcss/vite` plugin — no tailwind.config; global styles in `src/index.css`, which force-disables `border-radius` everywhere by design).

Song content lives in a single reducer (`lib/songReducer.ts`) driven from `src/App.tsx` via `useReducer(historyReducer)`. `App.tsx` is a composition root only — each UI concern is a custom hook in `src/hooks/` owning its own state, refs, and effects: `useToast`, `usePlayback` (scheduler + playhead + `tracksRef`), `useSelection` (selection rect, `gridRef`, document-level deselect), `useClipboard` (cell/section copy-paste, OS-clipboard mirror), `useGridEditing` (the grid keydown map + global undo/redo listener), `useSongLibrary` (IndexedDB hydration/`hydrated`, autosave, import conflicts, export/import). Abbreviated identifiers are banned in App/hooks and in shared type fields — `CellPos`/`Playhead` use `measure`/`column`/`stringIndex`, `Rect` uses `startColumn`/`endColumn`/`startString`/`endString`, and reducer actions use full-word fields (`set-cell` takes `measure`/`column`/`stringIndex`); the reducer's internal mirror math keeps short index locals by design. `SongState` carries `updatedAt` (stale between saves; save paths stamp `Date.now()`). Deployment: `vite.config.ts` sets `base: "./"` and `.github/workflows/deploy.yml` publishes `dist/` to GitHub Pages on push to main (repo Settings → Pages → Source: "GitHub Actions", one-time). Child components in `src/components/` are purely presentational and receive state + callbacks as props. `lib/youtube.ts` declares the `window.YT` global (typed `YouTubePlayer`/`YouTubeNamespace`) so nothing casts `window`. Pure logic lives in `src/lib/`:

- `types.ts` — core model: a `Song` has `tracks` and `sections`, plus an optional `youtube` reference-video anchor and an optional `measureNotes` (string array, one free-text annotation per measure, shared across tracks — not per-track). A `Track` has a `tuning` (array of `{noteIndex, octave}`, row 0 = top string as drawn), `measures`, an optional `volume` (0–1 synth mix gain, absent = 1), and optional `strums` — per-column strum marks (`StrumRow` per measure, parallel to `measures` but lazily grown, so shorter/absent = unmarked; read through `songOps.strumAt`). A mark is a `Strum` string of 1–4 strokes (`"d"`/`"u"`, e.g. `"du"`) that split the column evenly — helpers in `lib/strum.ts`; the first shape stored `"down"`/`"up"`, which `normalizeStrum` migrates on load. D / U append a stroke to the focused column (`addStroke`; a fifth starts over) via `set-strum`, mirrored like any content write; Delete clears strums over whole columns or over a range with no frets in it; Shift+Delete (`clear-strums`) clears only the strums in the selected columns, keeping the frets. The grid draws an arrow row under the strings once the track has any mark, playback rolls each stroke's notes 14ms apart (down = bottom row first) with each stroke cutting the previous one, and a mark on a column with NO frets re-strums the last chord played before it in arrangement order (`progression.soundingCellsAt`/`isRestrum` — a restrum also cuts that chord's sustain), so a held chord is typed once and strummed many times, whole-column copy/cut/clear and section copy carry them, and both exports print them (text: a `D`/`U`/`DU` line under the strings, widening the column to fit; PDF: one arrow per stroke under the staff). `Section.comment` (song-wide) has no editor anymore — only `trackComments` are exported. Stems are NOT track-based — `Song.stems` is a list of `SongStem` audio layers (base64 ogg/mp3 saved inside the song JSON, numeric `nextId()` id, own `volume`) that play alongside the synth from measure 0 at song tempo; a stem needs no tabbed counterpart (e.g. drums, or the untabbed rest of a song) — that shape was chosen by explicit request over per-track stems. There is no vocal/lyric track kind — every track is the strings model; that variant was removed by explicit request in favor of `measureNotes`. Lyrics are `Song.lyrics` instead — song-wide (not per-track) `StepLyrics`: keyed by WHERE they are sung, `${entryId}:${pass}` (a progression step + pass of its repeat) → `LyricRow`s by measure offset into that step's section, one word/syllable per column — NOT by source measure, by explicit request, so a reused or repeated section gets its own words (the first per-source-measure array shape is migrated in `storage.migrateMeasureLyrics`, copied onto every step/pass playing those bars). `set-lyric` takes `entryId`/`pass`/`offset`/`column`; insert/delete-measure splice the rows of every step playing the owning section (`spliceStepLyrics`), and removing a step drops its lyrics (`pruneStepLyrics`); section copy does not carry them. In the grid a block shows one lyric row per pass (`1.`/`2.` for repeats) once anything is sung: L, clicking the row, or the section header's `+ lyrics` button opens an inline input (`TabGrid`'s `LyricEdit` {slot, pass, measure, column}, state held in App); Space/Tab commits and moves on in PLAY order (through every pass before the next block), Shift+Tab / Backspace-on-empty go back, Enter/Esc leave; words spill right over empty columns and the word under the playhead (matched on pass too) lights. In both exports a repeat sign only covers passes sung with the SAME words (or none): `trackSheetSections` splits a folded block into runs of identical lyrics, so passes with different words are written out one after another, each with its words under the strum line (`TrackSheetSection.verses` — never stacked verses over a ×N, by explicit request). A `Measure` is 8 columns (`COLS_PER_MEASURE`) of per-string values (`string | null`), encoded by `lib/cellValue.ts`: `"5"` plain, `"<7>"` harmonic (toggled with H, drawn `◇7`, exported verbatim, played at the natural-harmonic node pitch above the open string — 12→+12, 7→+19, 5→+24, 4/9→+28, others octave), `"5=2"` sustained (rings 2 bars; S cycles 1/2/4/off), `"<7>=2"` both. `Section.linkTo` (live) points a section at the root section it mirrors. `Song.progression` is the arrangement — an ordered list of `ProgressionEntry` `{id, sectionId, repeat}` steps; absent means each section once in timeline order, and the reducer materializes it on `load-song` so `SongState.progression` is always real.
- `lib/songReducer.ts` — the only structural writer: tagged-union `SongAction` cases plus the undo `historyReducer` wrapper (past/present/future, cap 100). Guarded no-ops return `state` identically. `coalesceKey` merges consecutive same-target edits (typing "1","2" → one undo step); keep keys narrow and per-field. `mirrorMeasures` fans a single-cell edit across a linked group (every linked copy, all tracks), so `set-cell`/`clear-range`/`paste-cells`/`set-measure-note` never touch linked content directly. Repeats are NOT mirrored content — a repeated section is one set of bars played several times by the progression, so there is nothing to keep in sync. `link-section` requires equal span between the two sections (a guarded no-op otherwise) and resolves to one ultimate root id (no indirection chains). The arrangement cases are `add-entry`/`remove-entry` (never the last step)/`move-entry`/`set-entry-repeat` (clamped 1–64), plus `set-lead-in` → `Song.leadInBars` (clamped 0–64): bars of silence before the tab comes in — pure playback timing, NO measures/sections behind it (a Silence-section version was rejected because its bars showed up editable in the grid); `usePlayback` starts stems/backings/video at the top of the shared clock and delays the synth timeline, rolling through the lead-in when playing from step 0 and skipping it when jumping to a cell, and every section-count-changing case keeps the progression in step: a new section is spliced in via `withNewSectionEntry`/`entryIndexForSection`, and `delete-section`/`delete-measure` run `normalizeProgression`. `delete-section` deletes the section AND its bars (a marker-only removal just merged the bars into the section above and was removed as useless — App confirms first, since it destroys content); `delete-section`/`delete-measure` clean up now-orphaned `linkTo`/`measureNotes` references rather than leaving them dangling; `insertBlankAt`/`insertSectionBlock` splice `measureNotes` in lockstep with `measureCount` on every measure-count-changing action.
- `lib/progression.ts` — the arrangement layer, and the only place the editor's coordinate system is defined. `buildSlots(ranges, progression)` expands the entries into `ProgressionSlot`s — one per PLAYED copy of a section (`repeatIndex`/`repeatCount`, the source `startMeasure`/`span`, and a `startStep` on the expanded timeline) — with sections no entry references trailing as `unused: true` slots so their bars stay editable and reachable. A "step" is one grid column on that expanded timeline: `stepOf(slot, measure, column)` and `locateStep(slots, step)` convert between steps and (slot, source measure, column), `slotForMeasure` picks which on-screen copy a measure means, and `playableSteps` is the end of playback (unused slots sit past it). Time also lives here: `Section.bpm` is a per-section tempo override (edited in the grid's section header, blank = song bpm, for matching a reference video whose performance drifts), so the step→seconds mapping is piecewise — `slotStepSeconds`/`secondsAtStep` integrate it, and playback, stem offsets, ring durations, the playhead glide (`stepDurationMs` from the current slot) and the video anchor all go through them instead of multiplying by one step duration. `normalizeProgression` drops steps for missing sections and falls back to one-per-section so a song can never render nothing; `entryIndexForSection` decides where a newly created section joins the arrangement.
- `lib/songOps.ts` — pure helpers: `sectionRangesFor`, `dedupeSections`, `measuresEqual`, and `insertMeasuresIntoTrack`/`deleteMeasuresFromTrack` — the only splice sites for a track's timeline (they splice `strums` along with the measures), plus the strum helpers `strumAt`/`strumRowsFor`/`writeStrums`.
- `lib/clipboard.ts` — `Rect` (global-column cell rectangle), `CellClipboard`/`SectionClipboard` payloads, OS-clipboard JSON round-trip (`parsePayload`; internal clipboard state is authoritative, OS mirror is best-effort). `SectionClipboard.measureNotes` carries per-offset annotations along with a copied section, same as `comment`/`trackComments`.
- `lib/exportText.ts` — ASCII export, walked in ARRANGEMENT order: `xN` comes straight off the progression entries, then folds further (consecutive steps with identical content merge, and a section that is k repetitions of a smaller unit prints the unit once — `findRepeatUnit`; a unit shorter than a line is then written out as many times as fit on one and divide the play count, even down to ×1, so a riff never shrinks below a line: a 2-bar riff ×8 prints 4 bars ×4, a section that is one 2-bar riff twice prints its 4 bars plainly). A sustained note prints its fret followed by `~` filler for the bars it rings (`ringFill`, cut by the next note on that string). Does not currently print `measureNotes`. The arrangement fold is exported as structured data too — `trackSheetSections(song, track)` (name/repeats/comments/measureIndices per block) and `ringFill` — which is what the PDF export draws from.
- `lib/pdf.ts` — sheet-style per-track PDF (`ExportPanel` buttons → App's `exportTrackPdf` → `downloadFile`; App imports it lazily so jsPDF stays out of the main bundle). `buildTrackPdf(song, trackId)` draws with jsPDF (the only place it's used; a hand-rolled PDF writer preceded it and was replaced by explicit request) as ONE CONTINUOUS system flow — `printedMeasures` flattens `trackSheetSections` into a measure list and lines pack `MEASURES_PER_LINE` at a time regardless of section boundaries, the real-tab-export look chosen over one staff block per section. Section names ride above the staff at the measure they start on (comments italic, wrapped onto their own rows under the name — each only as wide as the room before the next comment — pushing the staff down rather than running over the measures), repeats are begin/end repeat barlines with dots and bold `×N` over the end bar (never heading text), plus: title + `track · tuning · BPM` subtitle, stacked TAB clef + tuning letters on every line, a played-bar number on every measure (`TrackSheetSection.startBar` counts every repeat pass and the bars of sections skipped as empty, so the bar after a 4-bar ×2 block is 9; the grid numbers each slot the same way from `slot.startStep`), thin+thick final bar, fret numbers knocked out of the string line (harmonics print `<7>`), a thin let-ring line above the string over a sustain's bars (`ringFill`), page numbers when it paginates. Pagination is planned before drawing (`layout` per line, then a `planned` list): when the line that closes a section (continuing one already on the page) would spill onto the next page, the page tightens instead — every line gap on it shrinks toward `MIN_LINE_GAP` and the last line may dip `SQUEEZE_INTO_FOOTER` into the footer band — so a section's ending never sits alone on a new page. Lines hold up to `MEASURES_PER_LINE` bars; the ExportPanel's "Each section on a new line" checkbox (`PdfOptions.sectionPerLine`, remembered at `tab-editor:pdf-section-lines`) cuts a line before every section start instead of flowing through. Within a bar each note sits at the START of its slot and the last slot ends at the barline (after a small lead-in pad, wider after begin-repeat dots), so faint grey beat lines through beats 1–4 and the barlines form one even grid — notes centered in their columns put the barline half a column early. Standard-font text is WinAnsi — `sanitize` maps anything outside to `?`.
- `lib/instruments.ts` — measure/track factory (`makeTrack`), `MEASURES_PER_LINE` (4) grid wrapping, id counter (call `advanceIdCounter` after loading persisted songs so new ids don't collide).
- `lib/tunings.ts` — MIDI/note-name conversion plus the tuning generator: presets are not a flat list but instrument × type × root (`TUNING_TYPES`, `rootsFor`, `tuningMidisFor` — Standard/Drop derived by transposing the E-standard shape down, Open from authored per-root shapes; guitar and bass). `defaultTuning()` is E standard guitar.
- `lib/audio.ts` — Web Audio playback (lazy singleton `AudioContext`): a short decaying triangle wave (`playNote(freq, time, duration?, volume?)`), and timeline-aligned layer playback (`startStem`, keyed by stem id or track id — same `nextId` space, no collisions) used by both `Song.stems` and `Track.backing` (an uploaded mp3/ogg of that track's real part: plays from measure 0 at song tempo and mutes the track's synth notes; a Karplus-Strong guitar synth and then a pitch-shifted note sampler were both built and rejected — the user wanted the recorded part, not an instrument imitation). `decodeAudio` caches buffers by payload object identity (pre-warmed by an `App` effect so first play is on time); `stopStems` generation-kills late decodes; `setStemVolume` retargets gain live.
- `lib/youtube.ts` — YouTube IFrame API loader (lazy, cached promise), video-id parsing (`extractVideoId`), and the anchor-measure ↔ video-seconds conversion that keeps the reference video locked to the tab timeline: `videoSecondsForStep` takes a step→seconds mapping (playback passes `secondsAtStep`, which integrates per-section tempo overrides), `videoSecondsForCol` is the constant-tempo special case.
- `lib/sectionColors.ts` — `tieColor(colorIndex)`: muted per-group colors for linked-section tie marks, lit for the dark ground; unrelated to playback or export.
- `lib/storage.ts` — song library in IndexedDB (`tab-editor`/`songs`, keyPath `id`; every library function is async) because localStorage's ~5MB quota can't hold stem audio — a legacy localStorage library is migrated into IDB once on first open and the old key removed. Only tiny metadata stays in localStorage: last-opened song id and a manual library order (`moveSong` swaps neighbors and pins the order; `listSongs` puts manually-ordered ids first, never-moved songs after them newest-first). `migrateSong` first advances the shared id counter past every id the stored song uses (entry ids come from the same counter), then folds both legacy repeat shapes into the progression — the global `Section.repeat` becomes that section's play count with NO bars written out, and the short-lived per-track `loops` field is dropped since its repeated bars were already materialized as real content — and migrates legacy track audio (`migrateLegacyTrackAudio`: the short-lived per-track `stem` becomes `backing` — same semantics — while the `sample`/`instrument` experiments are stripped); `parseSongsJson` runs `migrateSong` at the import border so old files are stored normalized — `linkTo` is a live, reducer-driven field, not a legacy shape; `resyncLiveFeatures` just self-heals it on load (re-mirrors from source) and materializes the progression. Song ids are `crypto.randomUUID()`; export is whole-library or per-song (`exportSong`) as minified JSON compressed with LZW (`lib/lzw.ts`: variable-width 9–16-bit codes, dict frozen when full, "TABZ"+version header; `.tabz` files), and import (`parseSongsFile`) accepts both compressed and legacy plain-JSON exports, split from `importSongs` so `App` can prompt (ImportConflictDialog) before overwriting ids that already exist — new ids import immediately; each conflicting id gets Overwrite / Lyrics only / Skip — Lyrics only keeps the saved song's tabs and lays the file's words onto it bar for bar along the played timeline (`progression.lyricsAlongTimeline`/`lyricsOntoTimeline`, since step ids differ between songs; the open song takes them via `replace-lyrics`, one undo step). There is no separate lyrics-import button (rejected). Autosave and manual save must NEVER call `listSongs` (deserializing every song's stem audio froze the browser) — they use `hasSong` (key-only `count`) and patch the `librarySongs` state in place. `App` starts on a blank song and hydrates the library + last-opened song from IDB in a mount effect, rendering `GhostScreen` (a pulsing skeleton of the real layout) until both resolve. Range sliders are restyled globally in `index.css` (hairline track, 3px accent caret thumb — the "position is a line" motif).

Key invariants:

- Every track has exactly `measureCount` measures; every column has exactly `tuning.length` entries; `measureNotes` (when present) stays parallel to `measureCount`. All structural edits go through reducer cases, which route through the `songOps` splice helpers.
- Sections are markers (`startMeasure`) over the shared measure timeline; ranges are derived (`sectionRangesFor`). The first section (sorted) must start at measure 0, section starts must be unique and in range — measure deletion re-clamps/dedupes them. `Section.linkTo` still mirrors content across a linked group via `mirrorMeasures` (and `link-section`/`unlink-section` still exist for songs that use it), but the link/unlink controls were removed from the UI by explicit request — the progression covers reuse now, so nothing new can be linked. Repeats are NOT duplicated bars: the progression plays one section N times, and there are no loop controls in the grid — that per-track loop feature was removed in favor of the arrangement.
- `ProgressionStrip.tsx` (pinned above the score in the Tab view) is a READ-ONLY ribbon of the arrangement — one inert chip per progression step, `×N` for repeats, the current step underlined. It has no buttons at all: insert/paste/link controls were deliberately removed from it, and neither it nor the Progression view navigates to the tab (pressing a progression row does nothing — both were removed by explicit request). Section paste now lives in the Progression view's "paste section" button, which appends the copied section at the end of the timeline.
- The grid renders the ARRANGEMENT, one block per progression step: App passes TabGrid only each entry's first pass (`shownSlots`, `repeatIndex === 0`), so a section played three times is ONE block tagged `×3`, and the playhead (mapped through `shownSlotIndex`) loops through it on every pass. Playback and the ProgressionStrip still use the full expanded `slots`. Repeat counts are set only in the Progression view (`ProgressionView.tsx`, reached by the Tab/Progression switch in the pinned bar), never in the grid.
- Selection is a `RangeSelection` `{anchor, focus}` rect over global SOURCE columns (`m * COLS_PER_MEASURE + c`) crossing measure boundaries; keyboard edits target `focus`. Because one source measure can be on screen in several slots, `useSelection` also tracks `activeSlot`: the range tint draws in every copy (they are the same bars) while the focus caret only draws in the active slot, and horizontal navigation walks the grid as drawn (`stepThroughShown`: expanded steps, skipping a repeat's later passes) so arrowing off the end of a repeated block lands in whatever the arrangement plays after its last pass. The grid's keydown handler must ignore events originating from `INPUT`/`TEXTAREA` (section name/notes/measure-annotation fields live inside the grid). The document-level mousedown listener deselects outside `[data-grid]`/`[data-keep-selection]` — the sticky utility bar, transport bar, and reference-video widget all carry `data-keep-selection` so they don't clear an active selection. The focused cell renders as a caret (`border-l-2 border-l-accent`), not a boxed outline — see DESIGN.md.
- Playback mixes all tracks over the EXPANDED timeline (`locateStep` maps each step back to the source measure holding the cells), and a sustained cell (`"5=2"`) is scheduled with a duration of its ring bars, cut short by the next note on that string; `Song.stems` start once at playback start (offset to the from-step) and play alongside the synth, and the reference video gets a once-a-second drift check against the audio clock (re-seek past 0.3s off) so buffering can't detune it from the tab. All mixing lives in the corner Sound panel (`YoutubeSync.tsx`), not in `TrackTabs` (which shows only the tuning readout, printed low→high by `tuningLabel`): the panel holds the reference video (attach/remove, sync-here, a sync readout row showing the anchor — `sync · #N ↔ m:ss.mmm` — with ±50ms nudge buttons that adjust `anchorSeconds`, player volume persisted at `tab-editor:yt-volume`), one row per tab track (backing-audio upload/remove plus volume — the scheduler reads volume/backing through `tracksRef` so changes apply mid-playback, and `setTrackVolume` also retargets a playing backing's gain), and one row per stem (volume live via `setStemVolume` during playback, remove), a single keyed "Add source" button that opens a chooser (YouTube video — only when none attached — or MP3/OGG stem; the two never have separate add buttons), and a master-volume slider in the panel header (persisted at `tab-editor:master-volume`, driving `setMasterVolume` — every synth note, stem, and backing routes through one master GainNode in `lib/audio.ts`). `applySong`'s `advanceIdCounter` call includes stem ids. The on-screen grid shows only the active track (switched via `TrackTabs`), never multiple tracks stacked at once. Clicking a cell during playback jumps playback to that cell (App wraps the selection handler; shift-clicks extend selection without jumping), and `startPlayback` kills any previous scheduler/stems before starting so mid-play restarts (scrub, jump) never stack two tick loops. Playback uses a lookahead scheduler in `usePlayback`'s `startPlayback` (the standard Web Audio pattern), not a naive setTimeout-per-note loop: a `tick()` on a ~25ms timer schedules any notes falling within a 150ms lookahead window onto the real audio clock (`playNote(freq, exactTime)`), so JS event-loop jitter (React renders, GC) can only delay how far ahead we schedule, never the audio itself; the visual playhead is updated via a separate `setTimeout` matched to each note's real scheduled time (the overlay glides with `transition: left <stepDurationMs>ms linear` — paced to the tempo via TabGrid's `stepDurationMs` prop, replacing the fixed 150ms ease that stuttered at slow tempos), tracked in `visualTimeoutsRef` and cleared alongside the main loop on stop. Because the glide carries the line INTO a column over the step before it, each playhead update fires one step early (except a line's first column and the first step played, which land on time) and every update is shifted by `outputLatency()` so the line tracks what is heard. A user stop/restart calls `stopNotes()` (`lib/audio.ts` tracks every scheduled synth voice) so lookahead-queued notes and sustains go silent at once; reaching the end (`finishPlayback`) lets the last notes ring. `TransportBar` (fixed to the viewport bottom, `z-50` — the bar is a stacking context, so its shortcut-help popover can never exceed the bar's own z; at `z-30` the Sound panel (`z-40`) painted over the popover) carries both playback (play/stop/BPM/scrub) and the add-measure/add-section actions in a three-column grid layout (`grid-cols-[1fr_auto_1fr]`, not a centered flex row) so the play button stays genuinely centered regardless of side-group width — the row is full-viewport-width (no `max-w` column) so +Measure/+Section hug the left screen edge and BPM/help the right, by explicit request; there is no standalone Clear action (redundant with the sidebar's "+ New"). `TrackTabs` + the Tab/Progression switch + `ProgressionStrip` are wrapped `sticky top-0` in `App.tsx` so the track switcher and the arrangement reference stay visible while a long tab's grid scrolls underneath — `TabGrid`'s section and line wrappers carry `scroll-mt-[190px]` so the playhead auto-scroll lands below the pinned bar, and the score body carries `mt-4` so normal scrolling always leaves a gap under the pinned bar too. Blocked actions toast instead of silently no-opping; destructive ops are undo-covered (`Ctrl+Z`), so only track/section/library delete confirm.
- `YoutubeSyncPanel` (`components/YoutubeSync.tsx`) is a floating widget, `fixed` to the bottom-right corner at `md:` and up (`bottom-16 right-4` — offset above the fixed transport bar so they never overlap); below `md` it drops to an in-flow block. `Song.youtube` holds one anchor point (`anchorMeasure`/`anchorSeconds`); playback seeks/plays the video from the computed time and pauses it on stop — the video does not independently drive the tab's clock.

Visual system (palette, type, component language) is recorded in `DESIGN.md` — read it before touching any component's styling; it documents the committed dark-plate, single-family-Inter world and the load-bearing structural patterns (sticky utility bar, fixed bottom transport, corner video widget, translating playhead rule, the caret-style focus/playhead language, the lucide-react icon set themed through `components/Icons.tsx`) so they don't drift back into ad hoc chrome or a reintroduced serif face.

UI copy style: keep labels terse — no explanatory placeholder text or hint paragraphs.
